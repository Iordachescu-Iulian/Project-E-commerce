Data model

Entity–relationship diagram

13 models in MySQL 8.0. A Product is one purchasable edition; the digital and physical editions of a game share gameSlug and are shown together.

Key relationships

  • User 1—N Address / Order; one optional Cart per user, one CartItem per product.
  • Category 1—N Product 1—N ProductImage / CartItem / OrderItem.
  • Order 1—N OrderItem and Order 1—N OrderStatusHistory; delivery and discount are optional FKs.
  • OrderStatusHistory.actorId references the administrator who changed the status.

Rules the model enforces

  • Order snapshots: shipping fields, product name, slug and unit price are copied at checkout so later edits cannot rewrite history.
  • Nullable OrderItem.productId: deleting a product keeps past orders readable.
  • PaymentEvent.stripeEventId is unique: the database itself guarantees webhook idempotency.
  • Money is Decimal(10,2); dates are server timestamps; all foreign keys are indexed.

Constraints the database enforces

ConstraintWhereWhy it is there
UniqueUser.email · Category.slug · Product.slug · Order.orderNumber · DiscountCode.codeOne account per email, one stable public URL per product and per category.
UniquePaymentEvent.stripeEventId · Order.stripePaymentIntentId · Cart.userId · CartItem(cartId, productId)Idempotent webhooks, one intent per order, one open cart and one line per product.
Cascade / RestrictChildren cascade with their parent; Product.categoryId, CartItem.productId and Order.userId restrict deletionRows that cannot exist alone disappear; a category in use or a customer with orders cannot vanish.

Architecture

Components, stack and startup

Responsibilities

  • Server Components render the catalog, category, product and account pages; data comes from src/server/queries/*.
  • Client Components own the search box, auth forms, address editor and future cart interactions.
  • API route handlers validate input with Zod, enforce auth/roles and call src/server/services/*.
  • Prisma singleton is the only database entry point; no Prisma import reaches a Client Component.

Stack justification

  • Next.js + React + Tailwind: one language and one process, responsive by default, accepted without prior approval.
  • MySQL 8.0.36: relational transactions for orders and stock; a project-local instance on port 3307 keeps the demo self-contained.
  • Stripe test mode: no live keys or real cards; signed webhooks prove the payment state server-side.
  • Local SVG covers: no external image dependency during the live demo.

Error contract — every handler

{ "error": "Invalid Stripe signature." }
  • 400 validation or signature failure · 401 no session · 403 wrong role or foreign address.
  • 404 unknown slug, product or order · 409 duplicate email or stock conflict.
  • 500 unexpected failure · 503 Stripe not configured.
  • Money is serialised as a decimal string, never a float, so 129.99 cannot become 129.989999 in JSON.
  • pageSize is clamped to 24 server-side; a larger value is accepted but capped, never trusted.

Critical flow

Payment sequence and stock update

Steps 1–6 — checkout

  • The server reloads the cart, validates stock and totals, creates an Order with status NEW and payment UNPAID, then creates a PaymentIntent with the server-computed amount.
  • The browser confirms the test card with Stripe.js. A redirect back to the site never changes the order: only the webhook does.

Steps 7–9 — webhook (implemented)

  • Raw body + stripe-signature verified with constructEvent; invalid → 400.
  • PaymentEvent.stripeEventId is unique, so a duplicate delivery returns duplicate: true and does nothing else.
  • One transaction marks the order Paid, sets paidAt, decrements stock conditionally and appends status history.

Failure and cancellation

  • payment_intent.payment_failed stores the event only; the order remains UNPAID.
  • If any stock decrement affects zero rows, the transaction rolls back and the order stays unpaid; Stripe retries.
  • Cancelling an order calls restoreStockForCancelledOrder, which increments stock exactly once and records the transition.

Verification at P2

  • A bad signature returns 400; a missing signature returns 400.
  • scripts/test-webhook.mjs sends a signed event twice: first duplicate:false, then duplicate:true.
  • An unknown order id is rejected and no order is marked paid.
  • Service tests cover paid marking, stock rollback, double-payment and single restoration.
